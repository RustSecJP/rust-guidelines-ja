# このガイドラインについて {#about}

アプリケーションやライブラリの開発者が、スケールする慣用的な Rust を書くための、実用的な設計ガイドライン集です。

バージョン: 2026.6

## メタ設計原則 {#meta-design-principles}

私たちは既存の質の高いガイドライン、特に [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html) を土台にし、
Rust 開発者がよく出会うトピックを扱います。ガイドラインがこの本に載るには、次の基準を満たしていることを求めます。

- [ ] { 安全性、COGs、保守 } に良い影響を与えること。つまり、該当する場合は次のことをしなければなりません
  - [ ] **安全性のベストプラクティス** を促し、リスクの元を防ぐ
  - [ ] **高いスループット**、**低いレイテンシ**、**少ないメモリ使用量** につながる
  - [ ] コードを **読みやすく理解しやすく** する
- [ ] 経験のある（3年以上の）**Rust 開発者の大多数がそのガイドラインに同意する** こと。
- [ ] Rust の初心者（4週間以上）にとって **十分に理解しやすい** こと。
- [ ] **実用的** であること。非現実的なガイドラインは守られないからです。

## 適用範囲 {#applicability}

_must_ と宣言されたガイドラインは常に守られるべきものです。一方、_should_ のガイドラインはより柔軟であることを示します。

とはいえ、チームはこれらのガイドラインを適切だと思う形で自由に採用できます。また、時には別のやり方をする正当な理由があるかもしれません。

すべての項目をプロジェクトに適用してみることをお勧めします。ある項目が意味をなさない場合は、連絡してください。その項目に
問題があって更新すべきか、適用されないか（その場合でも、そうした例外的なケースを示すために更新するかもしれません）のどちらかです。

> ### <tip></tip> 黄金律 {#the-golden-rule}
>
> ここにある各項目には、それぞれ理由があります。大切なのは文字ではなく精神です。
>
> ガイドラインを回避しようとする前に、そのガイドラインがなぜ存在し、何を守ろうとしているのかを理解すべきです。
> 同じように、ガイドラインに従うことがその根底にある動機に反することが明らかになったなら、盲目的に従うべきではありません！

## 新しいガイドラインの提案 {#submitting-new-guidelines}

安全性、COGS、保守性の向上につながる実践的なガイドラインをお持ちですか？ぜひお聞かせください！
次の手順に従ってください。

- あなたのガイドラインが上記の [メタ設計原則](#meta-design-principles) に沿っているか確認してください。
- あなたの提案が [API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html) や [Clippy](https://rust-lang.github.io/rust-clippy/master/?groups) ですでにカバーされていないか確認してください。
- [PR か issue](https://github.com/microsoft/rust-guidelines) を作成してください。
